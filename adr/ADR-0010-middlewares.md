# ADR-0009: ترتیب Middlewareها و انتخاب Rate Limiting مبتنی بر حافظه

## وضعیت

Accepted

---

## زمینه

در این پروژه چند Middleware برای پردازش درخواست‌ها استفاده می‌شود؛ از جمله:

- CORS
- Request ID
- Logging
- Rate Limiting

ترتیب اجرای Middlewareها مستقیماً روی رفتار برنامه تأثیر می‌گذارد. علاوه بر آن، برای جلوگیری از ارسال تعداد زیاد درخواست از سمت یک Client، نیاز به Rate Limiting وجود داشت. در فاز فعلی پروژه یک پیاده‌سازی ساده مبتنی بر حافظه (In-Memory) انتخاب شده است.

---

## تصمیم

### ۱. ترتیب Middlewareها

Middleware مربوط به CORS باید قبل از Rate Limiting اجرا شود.

به این ترتیب حتی اگر یک درخواست به دلیل عبور از محدودیت تعداد درخواست‌ها با وضعیت `429 Too Many Requests` رد شود، Headerهای مربوط به CORS همچنان در Response وجود خواهند داشت و مرورگر می‌تواند پاسخ را دریافت کند.

در صورتی که Rate Limiting قبل از CORS اجرا شود، پاسخ 429 بدون Headerهای CORS به مرورگر بازگردانده می‌شود و مرورگر به جای نمایش خطای واقعی، درخواست را به عنوان یک خطای CORS گزارش می‌کند. این موضوع فرآیند عیب‌یابی را دشوار کرده و علت اصلی خطا از دید Client مخفی می‌ماند.

بنابراین ترتیب کلی Middlewareها باید به گونه‌ای باشد که Middlewareهای عمومی مانند CORS ابتدا اجرا شوند و Middlewareهای محدودکننده یا امنیتی بعد از آن قرار گیرند.

---

### ۲. Rate Limiting

در این مرحله از پروژه از یک ساختار داده In-Memory (`dict`) برای نگهداری زمان درخواست‌های هر IP استفاده شده است.

برای هر IP، زمان درخواست‌های اخیر ذخیره می‌شود و در هر درخواست جدید، فقط درخواست‌هایی که در بازه زمانی مشخص قرار دارند بررسی می‌شوند. اگر تعداد آن‌ها از حد تعیین‌شده بیشتر باشد، درخواست با وضعیت HTTP 429 رد می‌شود.

این پیاده‌سازی برای مرحله فعلی پروژه کافی است زیرا:

- برنامه تنها روی یک Process اجرا می‌شود.
- هدف، یادگیری منطق Rate Limiting است.
- وابستگی جدیدی مانند Redis وارد پروژه نمی‌شود.
- پیاده‌سازی بسیار ساده و قابل فهم است.

---

## گزینه‌های بررسی‌شده

| گزینه | مزایا | معایب |
|--------|--------|--------|
| In-Memory Dictionary | بسیار ساده، بدون وابستگی خارجی، مناسب توسعه و آموزش | بین Workerها مشترک نیست، با Restart پاک می‌شود، مقیاس‌پذیر نیست |
| Redis | اشتراک‌گذاری وضعیت بین تمام Workerها، سرعت بالا، مناسب Production | نیازمند سرویس جداگانه و پیچیدگی بیشتر |
| Database | وضعیت پایدار و ماندگار | کندتر، فشار بیشتر روی پایگاه داده، مناسب Rate Limiting نیست |

---

## پیامدها

### مزایا

- پیاده‌سازی ساده و قابل فهم.
- بدون نیاز به زیرساخت اضافی.
- مناسب برای فاز آموزشی و محیط توسعه.
- امکان تست سریع رفتار Rate Limiting.

### معایب

- اطلاعات Rate Limit فقط داخل حافظه همان Process نگهداری می‌شود.
- در صورت Restart برنامه تمام اطلاعات از بین می‌رود.
- اگر برنامه با چند Worker اجرا شود، هر Worker وضعیت مستقل خود را خواهد داشت و محدودیت به‌درستی اعمال نمی‌شود.
- برای محیط Production قابل اتکا نیست.

---

## برنامه آینده

در هفته ۱۱ این پیاده‌سازی با Rate Limiting مبتنی بر Redis جایگزین خواهد شد.

استفاده از Redis باعث می‌شود:

- تمام Workerها وضعیت مشترکی داشته باشند.
- اطلاعات پس از ایجاد Process جدید از بین نرود.
- Rate Limiting در محیط‌های چندسروری نیز به درستی عمل کند.
- امکان استفاده از الگوریتم‌های استاندارد مانند Sliding Window یا Token Bucket فراهم شود.
