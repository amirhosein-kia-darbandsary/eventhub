# ADR-0001: Use FastAPI as the web framework

## Status
Accepted

## Context
پروژه‌ی EventHub نیاز به یک وب‌فریم‌ورک برای ساخت API رزرو بلیت داره که باید:
- تحت concurrency بالا (چند نفر هم‌زمان روی یک صندلی/بلیت) درست رفتار کنه
- validation قوی روی ورودی/خروجی داشته باشه (چون سفارش‌های ناقص یا نامعتبر
  مستقیماً پول واقعی رو تحت تأثیر قرار می‌ده)
- مستندسازی API خودکار داشته باشه، چون این پروژه قراره frontend/mobile
  جداگانه‌ای مصرفش کنه
- امکان نوشتن background jobs (پردازش پرداخت، ارسال ایمیل) رو به‌سادگی بده

## Decision
از FastAPI 0.11x + Python 3.12 استفاده می‌کنیم.

## Alternatives Considered

| گزینه | مزایا | معایب |
|---|---|---|
| **Flask** | ساده، بالغ، اکوسیستم بزرگ | async پشتیبانی native نداره (نیاز به Quart یا افزونه)؛ validation دستیه (نیاز به marshmallow/pydantic جدا)؛ مستندسازی API خودکار نداره |
| **Django + DRF** | باتری‌های کامل (admin, ORM, auth)، بالغ‌ترین اکوسیستم | سنگین‌تر برای یک API-only سرویس؛ async هنوز به‌طور کامل native نیست (بخشی از ORM هنوز sync-first)؛ برای پروژه‌ای که هدفش یادگیری async عمیق FastAPI هست، انتخاب مناسبی نیست |
| **FastAPI** | async native؛ validation از طریق Pydantic built-in؛ مستندسازی OpenAPI خودکار؛ dependency injection ساده برای چیزهایی مثل auth و db session | اکوسیستم جوان‌تر از Django؛ بدون ORM/admin داخلی (باید SQLAlchemy رو جدا اضافه کنیم)؛ برخی الگوها (مثل background workers پیچیده) نیاز به کتابخانه‌ی جدا (Celery/arq) دارن |

## Consequences

### مثبت
- validation ورودی/خروجی به‌صورت خودکار از طریق Pydantic models، که ریسک
  bugهای مربوط به داده‌ی نامعتبر رو کم می‌کنه
- مستندسازی Swagger/OpenAPI رایگان، بدون نیاز به نگه‌داری دستی
- async از پایه، که برای این پروژه (چندین درخواست هم‌زمان روی منابع محدود
  مثل صندلی) ضروریه

### منفی / ریسک
- باید ORM (SQLAlchemy) و session management رو خودمون جدا مدیریت کنیم؛
  کار اضافه‌تری نسبت به Django داره
- تیم نیاز داره async/await رو درست بفهمه، وگرنه ریسک اشتباهاتی مثل
  block کردن event loop با کد sync وجود داره
