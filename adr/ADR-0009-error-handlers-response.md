# ADR-0008: استانداردسازی ساختار پاسخ خطا

## وضعیت

Accepted

---

## زمینه

در نسخه‌های اولیه پروژه، خطاها به صورت مستقیم با `HTTPException` مدیریت می‌شدند و هر Endpoint می‌توانست پاسخ متفاوتی تولید کند.

این موضوع باعث می‌شد:

- ساختار پاسخ خطا یکنواخت نباشد.
- Client مجبور به مدیریت چندین قالب مختلف شود.
- منطق دامنه به FastAPI وابسته گردد.

---

## تصمیم

تمام Exceptionهای دامنه از کلاس پایه `AppError` ارث‌بری می‌کنند و دیگر وابستگی مستقیمی به `HTTPException` ندارند.

یک Exception Handler سراسری مسئول تبدیل Exceptionهای دامنه به پاسخ HTTP مناسب است.

علاوه بر Exceptionهای سفارشی، خطاهای اعتبارسنجی Pydantic نیز توسط Handler سراسری به همان ساختار تبدیل می‌شوند.

تمام پاسخ‌های خطا از قرارداد زیر پیروی می‌کنند:

```json
{
    "code": "RESOURCE_NOT_FOUND",
    "message": "Venue not found.",
    "details": null
}
```

---

## گزینه‌های بررسی‌شده

| گزینه | مزایا | معایب |
|--------|--------|--------|
| استفاده مستقیم از HTTPException | ساده و مناسب پروژه‌های کوچک | وابستگی Business Logic به FastAPI، پاسخ‌های غیر یکنواخت |
| Exceptionهای دامنه + Handler سراسری | جداسازی مسئولیت‌ها، پاسخ یکنواخت، توسعه‌پذیری بیشتر | نیاز به پیاده‌سازی اولیه بیشتر |

---

## پیامدها

### مزایا

- تمام Endpointها از قالب یکسان برای خطا استفاده می‌کنند.
- Client همیشه ساختار ثابتی دریافت می‌کند.
- منطق دامنه مستقل از FastAPI باقی می‌ماند.
- افزودن Exceptionهای جدید تنها با تعریف یک کلاس جدید انجام می‌شود.
- اعتبارسنجی‌های Pydantic نیز با همان ساختار به Client بازگردانده می‌شوند.

### معایب

- نیاز به نگهداری Exception Handler سراسری.
- تعداد کلاس‌های Exception نسبت به استفاده مستقیم از HTTPException بیشتر می‌شود.

---

## نتیجه

استفاده از Exceptionهای دامنه همراه با Exception Handler سراسری باعث جداسازی مناسب لایه Business از لایه HTTP شده و قرارداد پاسخ خطا را در کل API یکپارچه می‌کند. این رویکرد علاوه بر افزایش خوانایی و قابلیت نگهداری، توسعه سیستم در آینده را نیز ساده‌تر می‌سازد.
