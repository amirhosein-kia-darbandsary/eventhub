# ADR-0015: Background Jobs — از `BackgroundTasks` به Dramatiq

## Status
Accepted

## Context
پروژه به یک مکانیزم برای اجرای کارهای غیرهمزمان با درخواست HTTP نیاز داشت (مثل ارسال ایمیل تأییدیه بعد از checkout، و پاکسازی دوره‌ای رزروهای منقضی). ابتدا از `BackgroundTasks` داخلی FastAPI استفاده شد.

با یک تست بار واقعی (k6، ۳۰ VU روی `POST /checkout` هم‌زمان با ۵ VU روی یک endpoint کاملاً بی‌ربط یعنی `GET /events`)، مشخص شد که `BackgroundTasks`:

- روی همون process و همون event loop اپلیکیشن اجرا می‌شه — هیچ ایزوله‌سازی واقعی نداره.
- اگه تسک به‌صورت `async def` تعریف بشه و داخلش یک فراخوانی *بلاک‌کننده* (مثل `time.sleep` معمولی، نه `asyncio.sleep`) باشه، مستقیم روی event loop اصلی اجرا می‌شه و کل اپلیکیشن رو قفل می‌کنه — حتی درخواست‌هایی که هیچ ربطی به اون تسک ندارن.
- در این تست، با ۳۰ تسک هم‌زمان (هرکدوم ۱۵۰ میلی‌ثانیه بلاک‌کننده)، لتنسی متوسط همه‌ی درخواست‌ها (`http_req_duration`) به بیش از ۴ ثانیه رسید (avg=4.06s, max=4.68s) — حدوداً برابر `30 × 0.15s`، یعنی دقیقاً نتیجه‌ی صف‌شدن سریالی تسک‌ها روی یک event loop واحد.
- اگه تسک sync معمولی باشه (نه async)، Starlette خودش اون رو در یک thread pool جدا اجرا می‌کنه — خطرش کمتره، ولی همچنان هیچ persistence و retry ای نداره.
- با یک ری‌استارت سرور، هر تسک صف‌شده که هنوز اجرا نشده، برای همیشه از بین می‌ره.
- هیچ visibility ای از وضعیت صف وجود نداره.

## Decision
مهاجرت به Dramatiq با Redis broker برای تسک‌های async (ارسال ایمیل تأییدیه، و بعداً پاکسازی دوره‌ای رزروهای منقضی با periodiq).

## Alternatives Considered

| گزینه | مزایا | معایب |
|---|---|---|
| `BackgroundTasks` (وضعیت اولیه) | صفر وابستگی اضافه، ساده‌ترین پیاده‌سازی | بدون ایزوله‌سازی واقعی؛ بدون persistence؛ بدون retry؛ زیر بار، کل اپلیکیشن رو تحت‌تأثیر قرار می‌ده |
| Celery | بالغ‌ترین و پرکاربردترین ابزار در اکوسیستم پایتون | وابستگی‌های سنگین‌تر (معمولاً به RabbitMQ نیاز داره برای بهترین عملکرد)، پیکربندی پیچیده‌تر برای یک پروژه در این مقیاس |
| Dramatiq (انتخاب ما) | سبک‌تر از Celery، مستقیم با Redis کار می‌کنه (که از قبل برای کش داشتیم)، retry و backoff built-in | اکوسیستم کوچک‌تر از Celery؛ کتابخونه‌ی Redis broker به‌صورت sync کار می‌کنه (نه async native) — نیاز به احتیاط اضافه (`run_in_threadpool`) در مسیرهای async |

## Consequences

### مثبت
- تسک‌ها دیگه event loop اصلی رو قفل نمی‌کنن؛ زیر بار مشابه (۳۰ VU هم‌زمان)، لتنسی درخواست‌های بی‌ربط دیگه تحت‌تأثیر قرار نمی‌گیره.
- Retry خودکار (`max_retries=3, min_backoff=1000`) باعث شد یک قطعی موقت واقعی و مستند‌شده‌ی اتصال به Redis (که در طول تست پیش اومد) به‌جای از‌دست‌رفتن تسک، فقط با ۳ ثانیه تأخیر دوباره تلاش بشه و نهایتاً موفق بشه.
- تسک‌ها حالا در Redis persist می‌شن؛ خاموش/روشن‌کردن worker باعث از‌دست‌رفتن تسک صف‌شده نمی‌شه (تست دستی شد: worker خاموش شد، تسک صف موند، worker دوباره روشن شد، تسک اجرا شد).

### منفی / ریسک
- **درس کلیدی که حین توسعه کشف شد:** چون Redis روی یک سرور راه دور اجرا می‌شه (نه هم‌مکان با اپلیکیشن)، هر فراخوانی sync به broker (`.send(...)`) در معرض idle-timeout شدن اتصال TCP قرار داره. در یک تست واقعی، این باعث یک خطای ۵۰۰ *ناپایدار* (intermittent) روی `POST /checkout` شد — گاهی reconnect به‌موقع (زیر ۱ ثانیه) موفق می‌شد، گاهی از `socket_timeout` رد می‌شد و کل درخواست fail می‌کرد.
- راه‌حلی که اعمال شد: (۱) `run_in_threadpool` دور `.send()` تا این فراخوانی بالقوه‌کند، event loop اصلی رو قفل نکنه. (۲) مهم‌تر، `try/except RedisError` دور همین فراخوانی — چون رزرو کاربر (`confirm_reservation`) قبل از این خط قبلاً commit شده، شکست صف‌کردن یک عملیات فرعی (ایمیل) نباید یک تراکنش اصلی و موفق رو به کاربر به‌صورت خطا نشون بده. در صورت شکست، فقط لاگ می‌شه.
- **ریسک باقی‌مانده:** این یعنی الان یک سناریوی نظری داریم که تسک ایمیل هیچ‌وقت صف نشه (اگه هم `.send()` و هم retry منطقی بعدی‌اش شکست بخوره) بدون این‌که کاربر یا سیستم متوجه بشه — فقط یک لاگ خطا ثبت می‌شه. برای production واقعی، این باید با یک آلارم/مانیتورینگ روی همین لاگ‌ها (هفته‌ی ۱۲) پوشش داده بشه.
- در production واقعی، broker باید هم‌مکان (یا با تأخیر شبکه‌ای بسیار کم) با اپلیکیشن باشه — دقیقاً همون درسی که هفته‌ی کش (Redis) هم گرفته بودیم، اینجا برای صف‌کردن تسک هم تکرار شد.
