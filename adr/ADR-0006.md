# ADR-0006: استراتژی Refresh Token به‌صورت Stateless

## وضعیت

پذیرفته شده (Accepted)

---

## زمینه (Context)

سیستم از Access Token و Refresh Token مبتنی بر JWT استفاده می‌کند.

دو رویکرد برای مدیریت Refresh Token بررسی شد:

- Stateless
- Stateful

---

## تصمیم (Decision)

در این مرحله از پروژه Refresh Tokenها به‌صورت **Stateless** پیاده‌سازی می‌شوند.

هر Refresh Token دارای زمان انقضا است و تا قبل از پایان اعتبار، سمت سرور وضعیت جداگانه‌ای برای آن نگهداری نمی‌شود.

---

## گزینه‌های بررسی‌شده (Alternatives Considered)

| گزینه | مزایا | معایب |
|--------|--------|--------|
| Stateless | پیاده‌سازی ساده، بدون نیاز به Redis یا Database، مقیاس‌پذیری بالا | امکان ابطال (Revoke) Token قبل از پایان اعتبار وجود ندارد. |
| Stateful | امکان Logout واقعی، ابطال Token در هر لحظه، کنترل کامل روی Sessionها | نیازمند نگهداری وضعیت Tokenها و افزایش پیچیدگی سیستم |

---

## پیامدها (Consequences)

### مزایا

- بدون نیاز به ذخیره Refresh Token در پایگاه داده
- عملکرد بهتر
- مقیاس‌پذیری بالا
- مناسب برای پروژه فعلی

### معایب

اگر حساب کاربر به خطر بیفتد یا نیاز به Logout اجباری باشد، تا پایان اعتبار Refresh Token همچنان قابل استفاده خواهد بود.

برای پشتیبانی از Revocation فوری لازم است معماری Stateful پیاده‌سازی شود.

در آن حالت:

- هر Refresh Token دارای یک `jti` خواهد بود.
- هنگام Logout یا Compromise شدن حساب، مقدار `jti` در Redis ذخیره می‌شود.
- هنگام استفاده از Refresh Token، ابتدا Redis بررسی می‌شود.
- در صورت وجود `jti` در Blacklist، Token رد خواهد شد.

این معماری امکان ابطال Token قبل از پایان زمان اعتبار را فراهم می‌کند اما نیازمند نگهداری وضعیت در سمت سرور است.
