# ADR-0010: هرم تست و مرز بین Service و Repository

## وضعیت

Accepted

---

## زمینه (Context)

در هفته‌های ابتدایی پروژه، منطق کسب‌وکار مستقیماً داخل Routerها و در کنار کدهای مربوط به دیتابیس قرار داشت. این موضوع باعث می‌شد تست کردن منطق برنامه دشوار شود، زیرا حتی برای بررسی یک قانون ساده نیز نیاز به اجرای یک پایگاه داده واقعی وجود داشت.

نمونه‌ی مشخص این مسئله، محاسبه‌ی `available` در TicketType بود. این مقدار صرفاً از یک فرمول ساده (`total_quantity - reserved_quantity - sold_quantity`) به دست می‌آید، اما به دلیل وابستگی مستقیم کد به دیتابیس، برای تست همین منطق نیز باید PostgreSQL واقعی راه‌اندازی می‌شد. این وابستگی سرعت توسعه و اجرای تست‌ها را کاهش می‌داد و باعث می‌شد Unit Testها عملاً به Integration Test تبدیل شوند.

در زمان جداسازی لایه‌ها، یک مشکل واقعی نیز شناسایی شد. در منطق ایجاد Event، وجود داشتن `venue_id` بررسی نمی‌شد و امکان ایجاد رویداد با یک Venue نامعتبر وجود داشت. این مشکل در زمان استخراج منطق از Router به Service آشکار شد و نشان داد که جداسازی منطق کسب‌وکار تنها برای تست‌نویسی نیست، بلکه باعث خواناتر شدن جریان برنامه و آشکار شدن باگ‌های پنهان نیز می‌شود.

بنابراین نیاز بود مرز مشخصی بین منطق کسب‌وکار، دسترسی به داده و لایه‌ی HTTP تعریف شود تا هر بخش مسئولیت مشخصی داشته باشد و بتوان آن را به صورت مستقل آزمایش کرد.

---

## تصمیم (Decision)

در این پروژه سه لایه‌ی اصلی تعریف شد.

- **Router** تنها مسئول دریافت Request، اعتبارسنجی اولیه، فراخوانی Service و برگرداندن Response است. هیچ قانون کسب‌وکار نباید در این لایه قرار بگیرد.

- **Service** محل قرارگیری تمام قوانین و تصمیم‌های دامنه است. اعتبارسنجی موجود بودن موجودیت‌ها، بررسی قوانین تجاری، محاسبات، هماهنگی بین چند Repository و تمام منطقی که رفتار سیستم را تعریف می‌کند، در این لایه قرار می‌گیرد.

- **Repository** تنها مسئول ارتباط با پایگاه داده است. این لایه عملیات خواندن و نوشتن داده را انجام می‌دهد و نباید شامل قوانین کسب‌وکار باشد.

برای جلوگیری از ایجاد Repositoryهای غیرضروری، قانون زیر به عنوان مرز پروژه تعریف شد:

| سؤال | تصمیم |
|------|--------|
| آیا منطق فقط یک عملیات ساده CRUD است؟ | مستقیماً از Session در Service استفاده می‌شود. |
| آیا این منطق در چند نقطه استفاده می‌شود یا Query پیچیده دارد؟ | Repository ایجاد می‌شود. |
| آیا این منطق نیاز به Mock/Fake مستقل در Unit Test دارد؟ | Repository با Protocol تعریف می‌شود. |

همچنین برای تعریف قرارداد Repositoryها از **Protocol** استفاده شد و نه کلاس‌های Abstract.

دلیل این انتخاب آن است که Protocol از Duck Typing پشتیبانی می‌کند؛ بنابراین هر شیئی که متدهای موردنیاز را پیاده‌سازی کند، بدون ارث‌بری صریح نیز قابل استفاده خواهد بود. این ویژگی ساخت Fake Repositoryها را در Unit Test بسیار ساده‌تر می‌کند و وابستگی غیرضروری بین کلاس‌ها ایجاد نمی‌کند.

---

## گزینه‌های بررسی‌شده (Alternatives Considered)

| گزینه | مزایا | معایب |
|--------|--------|--------|
| استفاده از Repository برای تمام عملیات‌ها، حتی CRUDهای ساده | ساختار کاملاً یکدست، آماده برای تغییر دیتابیس یا افزودن Cache در آینده | Boilerplate زیاد، افزایش تعداد فایل‌ها و کلاس‌ها، پیچیدگی غیرضروری برای عملیات‌های ساده |
| استفاده از Repository فقط برای منطق واقعی (انتخاب پروژه) | کد ساده‌تر، کاهش Boilerplate، Repository فقط جایی ساخته می‌شود که ارزش معماری دارد | ظاهر پروژه کاملاً یکنواخت نیست و لازم است مرز استفاده از Repository مستند شود |
| استفاده از Abstract Base Class (ABC) به جای Protocol | قرارداد صریح و آشنا برای بسیاری از توسعه‌دهندگان | نیاز به ارث‌بری اجباری، انعطاف کمتر در ساخت Fakeها، ناسازگارتر با Duck Typing |

---

## پیامدها (Consequences)

### مزایا

- منطق کسب‌وکار از لایه‌ی HTTP جدا شد و هر بخش مسئولیت مشخصی پیدا کرد.
- تست‌های Unit بدون اجرای PostgreSQL و بدون وابستگی به زیرساخت قابل اجرا شدند.
- اجرای پنج Unit Test تنها حدود **۱٫۲۶ ثانیه** زمان برد و هیچ پایگاه داده‌ای در آن دخیل نبود.
- باگ واقعی مربوط به بررسی نشدن `venue_id` هنگام ایجاد Event در همین فرآیند شناسایی و اصلاح شد.
- استفاده از Protocol نوشتن Fake Repositoryها را ساده‌تر کرد و وابستگی به پیاده‌سازی واقعی دیتابیس کاهش یافت.

### معایب / ریسک

- مرز بین «Repository لازم» و «Repository غیرضروری» کاملاً بدیهی نیست و توسعه‌دهندگان جدید باید این قانون پروژه را یاد بگیرند.
- اگر این مرز رعایت نشود، پروژه ممکن است به دو سمت نامطلوب حرکت کند؛ یا Repositoryهای غیرضروری برای هر CRUD ساده ایجاد شوند، یا منطق کسب‌وکار دوباره داخل Routerها و Queryهای دیتابیس پخش شود.
- نگهداری این معماری نیازمند مستندسازی مداوم و پایبندی تیم به همین قوانین است تا ساختار پروژه در طول زمان یکپارچگی خود را حفظ کند.
